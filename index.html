⚠️

Brief Pressure-Test: Should Caretakers See Their Own Reviews?

The brief asks us to validate: "caretakers get reports on reviews from bookings they hosted." Our finding: this is risky without attribution filtering. 55% of complaints in this dataset are property/maintenance issues — the caretaker cannot fix them. Showing caretakers a negative review about pool hygiene or heating creates false accountability and demoralises good hosts. The safer model: caretakers see only caretaker-attributable feedback (check-in, guest communication, cleanliness inspection sign-off) — not the full review. Ops keeps the full view. More detail in the Spec tab.

AI Agent Spec

Problem framing · stakeholder design · trade-offs · risks

🎯 Problem Framing

Spacez has a signal aggregation problem, not a data collection problem. Reviews exist across three platforms, but because nobody synthesises them, three failure modes emerge:

  • Issues recur because no one sees the pattern across platforms and properties
  • Blame is misattributed — caretakers get penalised for HVAC failures; properties get flagged for caretaker habits
  • Hospitality quality is invisible at portfolio scale — Business can't distinguish a structurally bad property from a bad week

The right output is not a report, it's an attributed action: the right issue, assigned to the right person, with the right context.

Note: The assignment dataset was not provided. This prototype uses a synthetic 46-review dataset created from the scenarios and seeded traps described in the brief.

👥 What Each Stakeholder Gets
🔧 Operations (this prototype)
Recurring issue list → attributed (property vs. caretaker vs. listing) → priority-ranked action items → assigned to right owner. Trigger: Weekly digest + immediate alert if 2+ reviews mention same issue within 30 days. Action it drives: Maintenance ticket, caretaker coaching, vendor SLA change.
📈 Business
Portfolio scorecard: normalised rating per property over time, platform distribution, occupancy-weighted NPS trend. Flags: properties consistently below 3.5 → exit or invest decision. Properties consistently 4.5+ → explore expansion. Action it drives: Pricing changes, CapEx decisions, platform de-listing. Distinct from Ops: Business sees trends, not incidents. They don't need to know pool pH — they need to know Serenity's margin risk.
👤 Caretakers
Filtered digest: only feedback attributable to caretaker behaviour (check-in, communication, cleanliness sign-off). Property issues (pool, heating, road) are excluded from their view. Framed as actionable coaching, not performance scores. Why filtered: Showing full reviews demoralises good caretakers for issues outside their control, and creates perverse incentives (avoiding bookings in off-season when heating complaints spike).
⚡ Caretaker Hypothesis: Verdict

Brief claim: "Caretakers should get reports on reviews from bookings they hosted."

Our verdict: Risky as stated. Safe only with attribution filtering.

Why it's risky:

  • 55% of complaints in this dataset are property/infrastructure issues the caretaker cannot fix
  • A Booking.com 6/10 for "broken heating" is not Priya's failure — showing it to her as performance data is unfair
  • The Lokesh pattern (cross-property check-in delays) is invisible if you only give each caretaker their own property's reviews — you need portfolio-level analysis first
  • Caretakers seeing raw ratings may game behaviour (inflate guest sentiment before checkout) or avoid difficult guests

When it's safe:

  • Reviews are pre-filtered to caretaker-attributable themes only
  • Framing is coaching-first ("guests noted check-in timing — here's context") not score-first
  • Caretaker sees qualitative excerpts, not raw normalised ratings
⚠ Risks & Pushback
Attribution is the hardest part
The entire value of this system depends on correctly assigning pool → maintenance, heating → HVAC, check-in → caretaker. Current: rule-based keyword matching. Risk: a broken pool pump described as "unclean" misattributes. Validate first with 50 manually-labelled reviews before automating attribution.
No ground truth for caretaker mapping
This prototype assumes we know which caretaker hosted which booking. If that data isn't in the PMS or reliably logged, the entire caretaker layer breaks. Validate: can Spacez export caretaker → booking mapping from their system?
46 reviews is thin signal
3 recurring issues in 46 reviews looks alarming. With 500 reviews, patterns are more stable. Alert thresholds should scale with volume. Also: seasonal patterns (heating in winter) may look like persistent issues. Weight recency, normalise by season.
What to validate first
  1. Does Ops actually act on weekly digests, or does it need real-time Slack pings?
  2. Do caretakers have smartphones / WhatsApp? Determines delivery format
  3. Can we access raw API data from Airbnb/Booking.com or only manual exports?
  4. Is there a PMS with caretaker → booking mapping?
📏 How We'd Measure Success
→ Recurring issue decay rate: does the same issue appear in 3+ consecutive months after an action item is generated? Target: 0 unresolved recurring issues by week 8.
→ Action completion rate: % of recommended action items closed within 14 days. Target: >70%.
→ Portfolio rating trend: normalised cross-platform avg rating, week-over-week. Target: +0.3 over 90 days.
→ False attribution rate: % of actions assigned to wrong owner (ops audits). Must stay below 10% for system trust.
→ Caretaker NPS (internal): do caretakers find their filtered feedback useful? Survey monthly. If below 7/10, the caretaker layer is net-negative.
